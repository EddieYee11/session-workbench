## 一、调研执行背景与全景系统边界

### 1.1 系统定位与专属业务边界

Com!（原名「会话工作台」）是 Eddie 深度自用的跨端个人 Agent 综合工作台与日常任务智能中枢。
根据用户最新明确指令，**Com! 的客户端形态仅聚焦于：随身折叠屏主力机 iPhone Duo（iOS 客户端）与 MBP 移动办公网页端（Web 客户端）**。旧工程及非目标端（如 Android `projects/session-workbench`）已被彻底弃用，不再纳入系统演进与 PRD 考量范围。

Com! 的核心业务使命定义为：**让 Eddie 在离开办公桌后，通过随身的 iPhone Duo 或轻量打开 MBP 网页，无缝掌控、推动 Mac mini 本地常驻的个人 Agent（Pi / Hermes / Codex）执行，并汇聚个人事务（邮件待跟进、日历日程、微信待回、Obsidian 行动台待办、日常记账）的统一随身工作入口**。

### 1.2 目标硬件形态与 iPhone Duo 专属折叠特性

iPhone Duo 苹果折叠屏（硬件标识 `iPhone19,4`）与普通直板手机及 iPad 具有截然不同的物理形态与交互隐喻。现存 iOS 代码库（`work/工具与效率/会话工作台/ios/Com/Views/RootView.swift`）已经为其搭建了分档响应式骨架：

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        iPhone Duo 折叠屏专属双形态映射 (RootView.swift)                 │
├──────────────────────────────────────────┬─────────────────────────────────────────────┤
│  1. 外屏闭合态 (Outer Single-Pane)       │  2. 内屏展开态 (Inner Dual-Pane Split)       │
│  - 物理规格: 5.4 英寸外屏, 窄屏竖持      │  - 物理规格: 7.6 英寸内屏, 展开横拿 / 悬停    │
│  - 阈值判定: screenWidth < 700pt        │  - 阈值判定: screenWidth ≥ 700pt (典型 951pt)│
│  - 布局机制: 典型单栏导航栈 (tabHost)    │  - 布局机制: splitContent 左右双栏同屏并列    │
│  - 导航隐喻: 底部悬浮/侧边 ComDock 切换  │  - 结构分布:                                 │
│  - 顶栏形态: 全局唯一 ComTopBar          │    * 左栏 (固定宽 360~420pt): Com 主聊天     │
│                                          │      顶栏挂载: ComTopBar(pinned: .chat)     │
│                                          │    * 中间铰链区: crease 留空 (半折叠避空)    │
│                                          │    * 右栏 (弹性铺满): 下一步 / 今天 / 工作   │
│                                          │      顶栏挂载: PaneBar(tab: rightTab)        │
│                                          │    * 最右侧系统边缘列: 竖排 ComDock          │
└──────────────────────────────────────────┴─────────────────────────────────────────────┘
```

#### iPhone Duo 核心硬件参数与代码映射：
1. **分栏分水岭阈值 (`splitMinWidth = 700pt`)**：
   - 当屏幕宽度 `< 700pt`（如闭合外屏竖拿，约 466pt；或内屏竖屏单列，约 669pt）时，系统处于**单栏模式**；
   - 当屏幕宽度 `≥ 700pt`（如内屏完全展开横拿，约 951pt）时，系统激活 **`splitContent` 双栏同屏**。
2. **左栏比例锚定 (`leftPaneWidth`)**：
   - 左栏固定为 Com 主聊天，宽度计算公式为 `min(420, max(360, (screenWidth * 0.42).rounded()))`，保证主对话始终拥有舒适的 380~420pt 黄金阅读行宽。
3. **物理铰链与折痕保护区 (`crease`)**：
   - 通过 `CreaseProbe` 实时监测 iOS 系统的 `GeometryProxy.reservedRegions(kind: .division)`。当处于半折叠（L 型悬停笔记本态）时，中间生成竖向 `crease` 矩形。
   - `RootView.swift:127-133` 强制在折痕上方覆盖不接触摸的透明保护层，左右两栏自动避开折痕留空，防止用户在铰链凹陷处发生误触。
4. **右边缘系统安全区导轨 (`SideRail` & `sideDock`)**：
   - 利用 Duo 展开横屏右侧的硬件安全区，将 `ComDock`（导航胶囊）垂直立于最右侧，为大屏内容让出完整的上下垂直滚动空间。

### 1.4 模型路由与 Magpie Vertex 赠金池硬性约束声明

本报告与后续所有重构方案必须坚决遵守以下**绝对硬性架构红线**：

1. **核心模型路由拓扑**：
   - **主交互对话**：走 Mac mini 本地 Pi 网关或 Hermes 运行时，默认调度 `opencode-go / deepseek-v4.1-flash`。
   - **后台高并发结构化抽取**（包括「下一步」建议生成、Runsheet 动作编排、看板卡片语义打标等）：统一通过 `backend/hermes_review.py` 中的 `review_json()` 机制，直连已配置的 **Magpie API 网关**（基地址从 `~/.pi/agent/models.json` 动态加载）。
2. **赠金池保护与零订阅原则**：
   - 所有模型调用严格限定在 **Magpie Vertex / Volcengine 赠金池** 内消耗。
   - **严禁在目标业务后端中引入任何第三方商业付费订阅模型 API 调用**（如不得硬编码个人付费 OpenAI / Claude 商业订阅 Key，不得建立任何绕开 Magpie 网关的高额计费外部依赖）。
   - 重构必须通过“小模型高效结构化抽取 + 本地启发式过滤 + 确定性状态机”达成产品目标，严禁通过“堆砌昂贵大模型长上下文推理”来掩盖底层工程缺陷。

## 二、主聊天（Main Chat）现状诊断

主聊天不仅是与个人 Agent 对话的窗口，在 iPhone Duo 展开态下，它更是作为**常驻左栏的核心工作台**。当前主聊天在交互心流、并发控制与端侧适配上暴露了以下严重缺陷：

### 2.1 C01: iPhone Duo 展开态下主聊天作为常驻左栏的“同屏孤岛”困境

- **代码精准定位**：
  - iOS 客户端：`work/.../ios/Com/Views/RootView.swift:171-215` (`splitContent`)；`PaneBar.swift:1-33`；`ChatView.swift:1-150`
- **复现与触发条件**：
  - 将 iPhone Duo 展开（横拿或悬停，屏幕宽度 ≥ 700pt），进入双栏模式。此时左栏固定展示 Com 主聊天，右栏展示「下一步」（看板 / 建议）。
- **底层机理与严重性剖析**：
  1. 在架构设计上，`RootView.swift` 已经成功实现了视觉上的物理分栏：
     ```swift
     HStack(spacing: 0) {
         NavigationStack { page(.chat, dock: false) }.frame(width: leftWidth)
         if gap > 0 { Color.clear.frame(width: gap) } else { Rectangle().fill(Palette.separator)... }
         tabHost(SectionTab.workspace, selection: Binding(get: { model.rightTab }, set: { model.tab = $0 }), sideDock: true)
     }
     ```
  2. 但在**数据流与操作联动**层面，两栏完全是两个彼此割裂的“孤岛”：
     - **无法拖拽交互**：用户在右栏看到一张极有价值的建议卡片（如“回复王总关于 Q4 方案的邮件”），无法通过手势直接将其拖入左栏的主聊天中说“帮我看看这个”；
     - **缺乏同屏焦点态**：左栏在打字输入时，右栏完全无感知；右栏卡片在执行时，左栏的主聊天界面不会产生任何聚焦高亮或动态上下文关联；
     - **上下文流转缺失**：左栏谈妥的事项，右栏看板无法实时原地长出一张卡片；右栏选中的事项，左栏输入框也无法直接引用其实体 ID。
  - **严重级别**：**P0（致命体验断层）**，耗费了折叠大屏的高昂硬件成本，却没有提供匹配的同屏协同生产力。

### 2.2 C02: 主聊天严格单轮串行死锁与长耗时阻塞

- **代码精准定位**：
  - 后端服务：`work/.../backend/conversation.py:696-702`；`conversation.py:346`
- **复现与触发条件**：
  - 智能体正在执行一项长耗时任务（如扫描 Obsidian 全库或排查日历冲突，耗时需 20~40 秒），此时用户突然有紧急短询问（例如：“今天晚上岩馆几点关门？”）。
- **底层机理与严重性剖析**：
  1. 后端调度器在设计上为了避免会话状态混乱，采用了极端的单轮死锁机制：
     ```python
     def active_user_message(self) -> str | None:
         """正在进行的那一轮（主对话一次只跑一轮）：turn_plan 不信模型给的 ID，挂到这条上。"""
         with self.db() as db:
             row = db.execute("SELECT id FROM messages WHERE role='user' AND status IN ('queued','sending','running') "
                              "ORDER BY created_at DESC LIMIT 1").fetchone()
     ```
  2. 当有任务处于 `running` 状态时，用户发送的所有新消息全部被打入 `status = 'queued'`，静止排在队列末尾。
  3. 系统缺乏“主从分支（Fork/Branch）”或“轻量优先插话”机制。如果用户不手动点击那个隐蔽的“中断”按钮，系统必须死死等待上一个长任务完整执行完毕、输出大段文本后，才慢吞吞开始回答那个紧急的小问题。
  - **严重级别**：**P1（高危）**，完全破坏了随身设备即时问答的核心体验。

### 2.3 C03: 单轮临时思考计划（TurnPlanner）与右栏看板的认知断层

- **代码精准定位**：
  - 后端服务：`work/.../backend/turn_planner.py:1-80`；`backend/conversation.py:628`
  - iOS 客户端：`ios/Com/Views/ReplyWidgets.swift`；`AppModel+Chat.swift:44-55`
- **复现与触发条件**：
  - 在主聊天中下达复合指令，系统触发 `turn_planner` 生成 3~6 步执行计划。
- **底层机理与严重性剖析**：
  1. `turn_planner` 是一套精巧的单轮执行规划器，会在模型回复前拆解出步骤（如 `[1. 查账本, 2. 算总额, 3. 输出]`），并随着工具执行实时打勾更新状态。
  2. 但这套计划的生命周期**被死死限制在单条消息的气泡内部**！
  3. 一旦对话轮次结束（`status = 'completed'`），这些步骤就被永远冰封在该条历史消息内。用户如果想将其中未完成的某一步“放入待办”或“移到右栏看板明天继续”，系统没有任何流转入口。
  4. 用户在左栏看着“思考清单”，在右栏看着“看板待办”，两者长得几乎一模一样，但数据完全不互通，造成强烈的认知断层。
  - **严重级别**：**P1（高危）**。

### 2.4 C04: 后台航程借道主聊强行插话破坏人机对话心流

- **代码精准定位**：
  - 后端服务：`work/.../backend/cases.py:323`；`backend/conversation.py:310`
- **复现与触发条件**：
  - 某个由右栏或后台派发的长耗时航程（Case）执行完毕，或者中途需要向用户汇报阶段性产物。
- **底层机理与严重性剖析**：
  1. 当后台独立航程完成时，`cases.py:323` 会调用 `conversation.task_receipt()`。
  2. 该方法不加区分地直接向主聊天的消息数据表强行插入一条气泡消息。

### 3.2 P02: 跨界面强行伪装与劫持（Forced Tab Hijacking）——双栏同屏下的荒谬暴露

- **代码精准定位**：
  - iOS 客户端：`ios/Com/Views/NextView.swift:94-128`；`NextView.swift:49`
  - Web 客户端：`web/js/core.js:616-619`
- **复现与触发条件**：
  - **场景 A（iPhone Duo 内屏双栏并列下）**：用户在展开的双栏中，左边看着主聊天，右边看着「下一步」看板。用户点击卡片上的动作“记一笔 午饭 38 元”。
  - **场景 B（iPhone Duo 外屏单栏下）**：用户在单栏「下一步」Tab 浏览，点击卡片动作。
- **底层机理与严重性剖析**：
  1. 客户端没有就地执行记账或日程 API，而是调用了：
     ```swift
     appModel.send(textOverride: "记一笔 38 元 午饭")
     appModel.selectedTab = .chat  // 强行把当前激活 Tab 切换为 .chat
     ```
  2. **在 iPhone Duo 双栏同屏下的极致荒谬感**：
     - 在内屏展开态下，左栏明明**已经实时并列展示着主聊天**！用户点击右栏的卡片，系统居然强制把右栏也切走、或者左栏突然被一条伪造的自己说的话刷屏！
     - 用户在右侧看看板的心流被粗暴打断；
     - **无法二次编辑参数**：若真实花费是 42 元而非建议上的 38 元，用户在卡片上没有任何修改输入框，点完就直接按错误金额作为已定事实发出；
     - **聊天历史污染**：主聊天被大量机械无趣的“记一笔”、“加个日程”刷屏，稀释并污染了真正的对话上下文。
  - **严重级别**：**P0（致命体验灾难）**。

### 3.3 P03: “交给 Com”的幽灵失踪事件（Ghost Delegation）

- **代码精准定位**：
  - 后端服务：`work/.../backend/cases.py:200-228`；`backend/app.py:2558`
  - iOS 客户端：`ios/Com/Views/NextView.swift:49`
  - Web 客户端：`web/js/core.js:616`
- **复现与触发条件**：
  - 用户在建议卡片上点击核心主按钮“交给 Com”（触发 `action: "discuss" | "delegate"`）。
- **底层机理与严重性剖析**：
  1. 前端代码写死约定：只要用户点了交办，立即执行 `selectedTab = .chat`，把界面切到主聊天。
  2. 然而在后端实现中：`cases.delegate()` 默认将任务封装为一个**独立的后台航程（Case）**并交由 Pi 进程执行，返回结构为 `{"mode": "case", "task_id": "xxx"}`。**后端根本没有向主会话 (`conversation`) 的数据表写入任何消息**！
  3. **后果**：用户被粗暴切到主聊天 Tab 后，面对空无一物的输入框和静止的屏幕发呆。Web 客户端甚至经常弹出 toast 报错：“已经丢进对话，但消息列表没刷齐”。
  4. 实际上任务已经在后台偷偷运行，但主聊天里没有任何卡片提示，用户误以为系统崩溃没点上，进而反复疯狂点击，导致后台产生大量重复的垃圾航程。
  - **严重级别**：**P0（致命）**。

### 3.4 P04: 看板卡片多态畸变与身份擦除（Identity Mutation）

- **代码精准定位**：
  - 后端服务：`work/工具与效率/会话工作台/backend/board.py:330-354`；`board.py:403-454`
  - iOS 客户端：`ios/Com/BoardModel.swift:105-182`；`ios/Com/Views/BoardViews.swift:350-420`
- **复现与触发条件**：
  - 用户在四列/三列看板中，将一张处于“建议”列的卡片长按拖拽至“待办”列。
- **底层机理与严重性剖析**：
  1. 系统在底层将这两列视为完全不同的两个宇宙：
     - “建议”列的真源是 `next-steps.sqlite` 中的 `items` 表，卡片 ID 为 `next:abc12345`。
     - “待办”列的真源是文件系统上的真实 Markdown 文件（`任务/待处理/xxx.md`），卡片 ID 为 `todo:def67890`。
  2. 当发生拖拽时，后端先调用 `next_to_todo()` 在磁盘上创建新的 Markdown 文件，然后把原 SQLite 中的建议标记为 `acted`。**卡片的实体 ID 瞬间发生了不可逆的突变**！
  3. 客户端为了保证拖拽丝滑，采用了乐观更新（Optimistic UI），在本地先保留旧 ID 挪到新位置。
  4. 当移动端再次发起操作，或者后台的 SSE/快照推送过来时，客户端本地的卡片 ID 与服务端的全新 ID 发生碰撞对不上，立刻触发 `BoardConflict`（HTTP 409 异常）。
  5. 导致卡片在用户松手后原地剧烈晃动，并弹窗提示：“没挪成，卡还在原处——可以再拖一次”，给用户造成严重的系统不可靠感。
  - **严重级别**：**P0（致命）**。

### 3.5 P05: “正在做”的虚假繁荣（The "Doing" Mirage）

- **代码精准定位**：
  - 设计文档契约：`work/工具与效率/会话工作台/docs/COM_NEXT_KANBAN_PLAN_20261103.md:38`
  - 后端服务：`backend/board.py:181-183`
- **复现与触发条件**：
  - 用户在看板中，将一张复杂的待办事项（如“起草周报草稿”）从“待办”列拖拽到“正在做”列。
- **底层机理与严重性剖析**：
  1. 依据 2026-11-03 看板会议中达成的妥协约定：“『正在做』= 只改状态，不自动交办”。
  2. 当用户将卡片拖入“正在做”后，后端仅仅是用正则表达式打开了对应 Obsidian 笔记的 Frontmatter，将 `状态: 待处理` 替换为 `状态: 进行中`。

  5. 这种“表面上看似在跑、背地里纹丝不动”的伪状态设计，是对用户信任度的极大摧残。

### 3.6 P06: 状态机缺失关键中间态导致异常分支脱落

- **代码精准定位**：
  - 后端服务：`backend/board.py:108-124`；`backend/cases.py:176-178`
- **复现与触发条件**：
  - 任务在执行过程中发生网络超时、需要提权确认、或者由于代码异常而终止。
- **底层机理与严重性剖析**：
  现有系统的状态流转极度简陋，缺乏工业级工作流所必需的中间缓冲态：
  1. **缺失 `executing`（执行中锁）**：点击交办后，建议状态直接跳跃为 `acted`。如果在生成航程或启动进程时容器挂了，该卡片已经在建议流中被抹除，用户再也找不回这个任务（任务在真空中凭空蒸发）。
  2. **缺失 `waiting_user_input`（挂起待确认）**：当后台航程因为需要删除文件或确认参数而挂起时，看板上的卡片依然呆板地显示为“进行中”，用户必须进入深层菜单才能发现它早已卡死在等待确认。
  3. **缺失 `error_retrying`（失败待恢复）**：一旦后台执行报错，卡片直接变成僵尸或凭空消失，没有原位重试机制。
  4. **缺失 `cancelled`（主动取消）**：用户无法明确废弃一个正在执行的任务并将其优雅归档。
  - **严重级别**：**P0（致命）**。

### 3.7 P07: 下拉刷新 30 秒卡死与语义去重失效

- **代码精准定位**：
  - 后端服务：`work/工具与效率/会话工作台/backend/next_steps.py:19-54`；`next_steps.py:114-120`
  - 客户端：`ios/Com/Views/NextView.swift:138-146`
- **复现与触发条件**：
  - 用户在「下一步」页面手动下拉刷新，或者后台每小时触发定时归纳。
- **底层机理与严重性剖析**：
  1. **同步巨石架构导致漫长卡顿**：`next_steps.refresh()` 采用了串行大石块设计，单次执行要依次读取 Gmail、日历、微信解密库、Obsidian、短信等 14 类信源，组装成带有 19 条复杂规则的超大 Prompt 丢给 Magpie。整个过程耗时高达 15 到 45 秒。在此期间，前端被迫展示生硬的虚拟倒计时进度条，界面近乎瘫痪。
  2. **启发式去重极其脆弱**：大模型每次生成建议时，标题具有高度随机性（例如上一轮叫“回复王总 Q4 排期邮件”，下一轮被重写为“跟进王总的排期确认”）。
  3. 后端的去重算法依赖最长公共连续汉字子串（`_cjk_runs` 需重合 60%）和依据标签交集匹配。一旦大模型稍作句式改写，去重算法立即失效。已经被用户划掉（dismissed）或标记不做的垃圾建议，在下一次刷新时立即以全新的标题“借尸还魂”，造成极度严重的骚扰。
  - **严重级别**：**P1（高危）**。

### 3.8 P08: 反向拖拽污染知识库笔记与破坏性数据修改

- **代码精准定位**：
  - 后端服务：`work/工具与效率/会话工作台/backend/board.py:403-454`
- **复现与触发条件**：
  - 用户在看板中，将一张原本在“待办”或“正在做”列的卡片，反向拖拽回“建议待办”（suggest）列。
- **底层机理与严重性剖析**：
  1. 用户将某项严肃待办移回建议，其本质期望只是“我现在不想做这个，让它退回观察池”。
  2. 但后端的处理逻辑极具破坏性：
     ```python

     todo_set_state(vault, rel_path, "已取消")
     # 凭空在 SQLite 插入合成假记录
     db.execute("INSERT INTO items (id, title, why, state) VALUES (?, ?, ?, 'open')", ...)
     ```
  3. 系统直接把用户 Obsidian 行动台库里的真实 Markdown 笔记改写为 `状态: 已取消`！这不仅污染了用户的本地知识库真源，甚至可能触发其他基于 Obsidian 状态同步的脚本产生误判（例如被归档清理脚本误删）。数据保全原则被严重践踏。
  - **严重级别**：**P1（高危）**。

### 3.9 P09: 垃圾积压与历史归档硬截断

- **代码精准定位**：
  - 历史事故记录：`work/工具与效率/会话工作台/docs/COM_NEXT_KANBAN_PLAN_20261103.md:18`
  - 后端服务：`backend/board.py:145-147`
- **复现与触发条件**：
  - 系统持续运行超过一周，产生了大量的已完成事项。
- **底层机理与严重性剖析**：
  1. **本地文件系统垃圾堆积**：在真实运行中，`任务/待处理/` 目录下曾堆积了 83 个 Markdown 任务文件，经过脚本对账发现其中 72 个其实在业务上早已完成，但从未被系统移走。原因在于系统完全缺乏自动归档机制（Auto-Archiving）。
  2. **前端暴力截断与历史黑洞**：在看板的“已完成”列，代码硬编码为：
     ```python
     cutoff = now - 2 * 86400  # 仅读取近 2 天
     done = done[:DONE_MAX]    # 仅展示最多 10 张
     ```
  3. 这种设计导致用户大前天完成的事情在手机上彻底人间蒸发。没有“查看历史”、“搜索已完成”的任何入口，用户若想回溯上一周的交付成果，必须退出 App 手动去翻 Mac 终端或文件管理器，严重违背了“个人随身中枢”的产品定位。
  - **严重级别**：**P2（中危）**。

### 3.10 P10: 乐观更新版本并发碰撞与 iCloud 8 秒超时熔断

- **代码精准定位**：
  - 后端服务：`backend/board.py:18` (`ICLOUD_TIMEOUT = 8`)；`board.py:91-93`；`board.py:274-275`
- **复现与触发条件**：
  - 当 Mac mini 正在与 Apple iCloud 同步大量 Obsidian 文件，且此时用户在手机端尝试拖动卡片。
- **底层机理与严重性剖析**：
  1. Mac 系统的 `bird` 守护进程在同步 iCloud 时，经常会对文件系统产生全局读写锁，导致普通的目录遍历和文本读取卡顿数秒至数十秒。
  2. 为了保护 FastAPI 事件循环不被拖垮，`board.py` 设置了 `ICLOUD_TIMEOUT = 8` 秒熔断。一旦读写超过 8 秒，直接抛出 `HTTP 503 Service Unavailable`。
  3. 客户端捕获到 503 时，由于缺乏优雅的本地脱机排队重试机制，卡片直接触发弹簧复原并报错，使得在弱网或高负载同步时，看板操作可用率急剧下滑。
  - **严重级别**：**P1（高危）**。

### 4.2 双栏同屏与单栏自适应的关键架构缺陷

当前系统在 iPhone Duo 和 Web 上的表现，暴露出两大核心架构缺陷：

1. **“物理上双栏同屏，逻辑上分时割裂”**：
   - 硬件和视图层（`RootView.swift`）已经提供了极为优越的双栏同屏容器（`splitContent`）。
   - 但是，上层业务逻辑仍然沿袭着旧时代“小手机单页面”的分时心智！典型的恶果就是：用户在右栏点击记账，系统居然还在调用 `selectedTab = .chat`！在双栏同屏状态下执行切 Tab，导致右栏内容突兀跳变，左栏平白无故吃进一句伪造的发言。这种代码逻辑与硬件物理形态的严重脱节，是造成用户体验“极度不适”的罪魁祸首。
2. **缺乏真正的端到端跨栏手势交互**：
   - 在 iPadOS 或现代折叠屏优秀 App 中，用户可以轻松将右侧看板的一张待办卡片，长按直接拖动跨过中间折痕、松手丢进左侧主聊天输入框，立刻触发“围绕该事项展开探讨”；
   - 现有的 `BoardViews.swift` 将手势识别完全局限在右栏内部的局部坐标系（`localCoordinateSpace`），根本无法跨越 `splitContent` 的分栏边界，白白浪费了双栏同屏的协同威力。

## 六、重构核心原则与设计假设输入

基于以上针对 iPhone Duo、Web 客户端与核心后端的详尽排查，为直接指导后续 R2 阶段产品重构方案与 PRD 规范的编制，特确立以下六大核心设计原则与工程假设：

### 6.1 原则 1：统一任务对象模型（Unified Matter Entity）
- **消除身份突变**：彻底废除 `next:<id>` 与 `todo:<id>` 之间的多态转换与实体突变。系统统一确立全局唯一的 **Matter（事项）** 对象模型。
- **唯一标识贯穿始终**：无论一条事项最初来源于外部邮件、微信提醒、日历变更、还是用户在主聊天中的随口交代，系统自生成之时即赋予其唯一的 `matter_id`（如 `mtr-20261106-xxxx`）。
- **属性化生命周期**：建议态（Suggested）、待办态（Todo）、进行中（Doing）、已完成（Done）是**同一个 Matter 对象上的状态属性流转**，绝不改变底层实体 ID，绝不因状态转移而在不同数据库与文件系统间破坏性地反复迁移或生成合成假数据。

---

### 6.2 原则 2：iPhone Duo 双栏同屏原生联动与就地闭环（Dual-Pane Co-Presence）
- **双栏同屏的协同基线**：
  - 在 iPhone Duo 展开态（≥700pt）下，系统必须充分利用左栏主聊天与右栏看板同屏并列的物理优势；
  - **原生跨栏拖拽交办**：支持将右栏的 Matter 卡片长按直接跨越中缝拖入左栏输入框，松手即自动挂载为对话上下文锚点（Linked Context）；
  - **同屏焦点联动**：当右栏某项任务处于 `executing` 时，左栏顶部挂起胶囊同步点亮，点击胶囊平滑滚动到该任务对应的聊天讨论段落。
- **严禁跨 Tab 强行伪装劫持**：
  - 无论处于内屏双栏还是外屏单栏，点击任何结构化动作（记账、加日程、回复邮件），**严格禁止切走当前 Tab，严格禁止向主聊天注入伪造发言**。
  - **就地微卡闭环交互**：点击动作后，在当前页面就地呼出半屏轻确认微卡（Micro-Sheet / Action Sheet）。展示提取出的结构化参数（如金额、分类、时间），允许用户秒级修正后点击“确认提交”；提交后直接调用底层领域专用 API（如 `fast_bookkeeping`、`calendar_bridge`），给出轻量 Toast 提示即完成闭环。

---

### 6.3 原则 3：完备且容错的有限状态机契约（Robust FSM）
彻底淘汰两值跳跃的简陋流转，设计覆盖全部分支的工业级有限状态机模型：

```
                    ┌───────────── SNOOZED (暂缓搁置)
                    │                ▲
                    │ (明日定时唤醒)  │ (稍后再说)
                    ▼                │
[SUGGESTED] ──────────► [TODO] ──────────► [DOING / EXECUTING]
(AI 建议推荐) (采纳)   (待办认领) (启动托管)     │
      │                   │                    ├────► [WAITING_INPUT] (挂起等待用户决策)
      │ (忽略划掉)        │ (主动放弃)         │            │
      ▼                   ▼                    │ (决策完成) │
[DISMISSED]         [CANCELLED]                │ ◄──────────┘
(已忽略归档)        (已取消归档)               ├────► [ERROR_RETRYING] (失败可恢复重试)
                                               │            │
                                               │ (执行成功)  │ (重试成功)
                                               ▼ ◄──────────┘
                                         [DONE]
                                         (已完成归档)
```
- 明确定义每个状态的进入条件、退出守卫、允许的操作行为与超时降级逻辑；
- 无论后台发生何种网络中断或代码异常，卡片均停留在明确的确定性状态，绝不允许任务在虚空中“静默失踪”。

### 6.4 原则 4：主对话“主线交互 + 顶部挂起条”并发模型
- **主客分离，专注心流**：主聊天界面回归纯粹的人机交互空间。长耗时、异步跑在后台的智能体航程（Case）不再通过强行插话破坏对话连贯性。
- **顶部实时挂起条（Live Presence Bar / Capsule）**：当有后台任务在推进时，主聊天顶部以极简动态胶囊展示当前正在执行的任务名称与实时步骤（如“正在梳理周报: 第 2/5 步”）；
- **即时打断与轻量并发**：在后台任务执行期间，用户可以随时在主输入框输入新问题或下达新指令，系统优先响应轻量问询，长任务继续在后台平稳推进，不再发生无脑排队锁死。

---

### 6.5 原则 5：增量流式通信基线与非破坏性数据保全契约
- **工业级 SSE 增量同步**：客户端连接携带 `Last-Event-ID: <rev>`。服务端仅推送自该版本以来的增量事件包（`delta`），并具备指数退避静默重连机制，彻底杜绝红字报错打断。
- **坚守知识库数据保全红线**：底层 Obsidian 行动台 Markdown 笔记作为用户的个人真源知识资产，严禁系统在反向流转时擅自将其状态改写为“已取消”或物理删除。高层建议只做视图映射，任何涉及删除或不可逆变更的操作，必须严格获得用户的显式确认。
- **生命周期垃圾回收与深度归档**：建立自动化日结周结归档机制；已完成事项提供完整的历史索引与跨月检索视图，彻底消灭“历史黑洞”。

### 6.6 原则 6：坚守 Magpie Vertex 赠金池与零商业订阅底线
- **维持既有技术路线**：重构方案严格维持现有的 Magpie 网关与 Vertex/Volcengine 赠金池技术路线。
- **严格成本控制**：所有信源归纳、Runsheet 动作编排与语义提取必须确保在现有基础设施预算内高可用运转，严禁在目标业务代码中引入任何需要商业付费订阅的外部大模型 API。
