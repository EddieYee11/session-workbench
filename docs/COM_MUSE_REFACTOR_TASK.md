## 2. 产品目标（要复刻的「手感」）

用户只在主对话框说话。系统自己判断：直接回答、边做边答、还是拆成后台任务。任务以对话里的一行小卡片出现，点进去看具体步骤。对用户来说，普通问题和交办事项之间没有「切换模式」的动作。

具体指标：

1. 一个入口：用户不需要先想「这是聊天还是任务」。
2. 不阻塞：派发后主对话立即可继续，用户可以连发消息。
3. 任务只在需要时露面：直接回答的问题不生成任务卡；完成的任务折叠成一行。
4. 可下钻：点任务卡进入二级页，看到当前动作、人话步骤、产物，并能补充要求或停止。
5. 状态真实：保持「已受理 ≠ 已开始 ≠ 执行结束 ≠ 验收通过」，但界面只用少数几种说法，细分放进详情页。

不要声称这是对 Meta Muse 内部实现的还原；这里只复刻其交互感受。

## 4. 设计规格

### 4.1 导航：三个底部入口

| 入口 | 回答的问题 | 内容 |
| --- | --- | --- |
| 对话 | 我要说件事 | Pi 主线；任务卡片、工作过程卡、结果卡都在消息流里 |
| 今天 | 现在要我做什么 | ①需要我决定 ②今日日程 ③账本摘要一行 ④「进行中 N 项」一行（进入任务台账） |
| 工作 | 我要直接指挥 CC / Codex | 项目目录、Agent、模型、正文；会话历史 |

- 「任务」不再是底部一级入口。任务台账作为二级页：入口为今天页的「进行中 / 全部工作」，以及任务卡点击后的详情返回路径。
- 「更多」不再占底部位置：改为顶栏右上角入口，打开原有 sheet（设置、权限与上下文、通知巡检等）。
- 日历和账本是高频动作：从今天页进入，并在对话输入区上方提供快捷入口（「记一笔」「今日日程」），不要藏在更多里。
- **内部路由名尽量保持不变**（`hermes` / `sources` / `activity` / `work`），只改入口可见性与文案，降低回归风险。
- 建立一致的返回：详情页返回到进入它的地方（对话 → 回到该消息位置；今天 → 回今天；任务台账 → 回台账）；通知巡检等二级页不再固定返回今天。

### 4.2 对话流内联任务卡

- 位置：挂在触发它的用户消息下方（沿真实 `origin_message_id` / `linked_tasks` 关系，不靠标题匹配）。
- 一行结构：状态图标 + 短标题 + 状态文字 + 箭头。点击进入任务详情。
- **只有派发的后台任务（`task_submit` 产生的 job）生成任务卡。** 以下不生成：直接回答、同一轮内的工具步骤（继续用现有 `AgentWorkCard`）、工作页里的自然聊天。
- 一条消息拆出多件事，则下方并排多张卡。
- 展示上限：每条消息下，状态为「在办」「等我」的卡最多展开 3 张，其余合并为「另有 N 项」；点击进入对应任务列表筛选。
- 「已结束」的卡折叠为一行：「✓ 标题 · 查看过程」；结果文字照常回到对话里（沿现有 durable outbox / 总结卡）。
- 「等我」的卡用 Amber 提示色；如果复用现有 `WorkProposalSection` 的成本很低，可直接在卡上放主操作，否则点击进入详情处理。
- 缓存与实时状态要有区分（沿用现有 freshness 表达，不要新增一套）。

### 4.3 任务详情页（二级页）

信息顺序（承接 1.7.1 已有方向，不要回退）：

1. **现在怎样 + 主操作**：当前阶段、最近一步、等待原因；允许／拒绝／继续／核实／停止，按真实状态给出。
2. **结果与产物**：结果文字（字号已增大）、产物卡（见 4.10）、完成条件与验收状态。
3. **步骤**：人话时间线（见 4.9），默认只展开最近几步，其余折叠。
4. **补充要求**：底部输入框，沿当前任务入持久输入队列（见 4.8）。
5. **来源与历史**：交办原文、约束、输入送达记录、完整执行指令，默认折叠。
6. 「进入执行会话」「回到交办消息」入口保留；来源未确认时只给会话入口。

### 4.4 用户可见状态映射（四类）

**只改展示分组与文案，不改后端状态值、不改状态机。** 判断沿用 `ledgerGroup()`，不要只看 `LedgerTask.status`。

| 用户看到 | 对应内部状态 | 备注 |
| --- | --- | --- |
| 在办 | `queued`、`dispatching`、`running`、`cancel_requested` | `cancel_requested` 显示为「正在停止」，确认终止后才显示已停止 |
| 等我 | `waiting`、`approval_required`、`proposed`、`paused`、`unknown`、`failed` | `unknown` 文案用「需要你核实」；`failed` 给出原因，不总能重发 |
| 待确认 | `execution_finished` 且未验收通过 | 不等于失败 |
| 已结束 | 满足 acceptance 的完成、`cancelled`、`rejected`、`expired` | 完成用 ✓ 区分；停止／拒绝／过期不得冒充完成 |

详情页里保留一条小进度条，表达「手机已保存 → 已受理 → 执行器已排队 → 原生真正开始 → 执行轮结束 → 验收」，并只高亮有证据的层级。

### 4.5 任务分类 `kind`（读取时派生）

- `chat`：工作页里用户主动与 Claude/Codex 的自然聊天。**不进入任务台账、不出现「待验收」、不走 Judge。**
- `job`：真正委派、有完成条件的活。进台账，可验收，生成对话内联卡。
- `decision`：需要用户拍板的事项（来自 job 的等待／审批／核实／失败／待验收，或没有 ledger 的主对话异常）。在今天页聚合。

实现方式：在前端映射层（`TaskLedger.kt`）与必要的后端序列化处，依据现有来源标记（人工 work chat vs `task_submit`）**派生**；旧记录按规则回填展示，不改库。派生规则和边界情况（来源缺失时的默认值）写进测试。

### 4.6 今天页分层

- 「需要我决定」只包含 `decision`，计数与卡片内容一致。
- 通知巡检结果移到「仅供知情」分区，不占决策卡展示位，也不计入「待你决定」数量。
- 在途工作、账本压缩成摘要行。
- 排序沿用：需批准 → 需处理／核实 → 失败 → 待验收；知情项最后。
- 手机日历权限、手机日历无日程、远端桥接不可用三种状态分别处理。

### 4.7 主 Agent 路由规则（写进 Pi 主线的提示词／工具策略）

先在核验阶段找到 Pi 主线提示词与 `task_submit` 的实际位置，再修改，不得猜。**不要为路由另加一个分类器回合**（会让每句话变慢），在主 Agent 同一轮内决定。

要加入的策略文本（可按现有提示词风格调整措辞，语义不变）：

```text
处理每条用户消息时，先选最短路径：
1. 直接回答；
2. 本轮内用工具很快完成；
3. 派发后台任务（task_submit）；
4. 补充到已有运行中任务；
5. 只问一个澄清问题。
默认选 1 或 2。仅当满足以下任一条件才派发：
- 预计超过约 30 秒；
- 需要在项目目录里修改、构建或测试文件；
- 可以拆成互不依赖、可并行的部分；
- 用户明确说「交给…／去做…」。
派发后立刻用一句话告诉用户拆成了几件事，不等待结果，主对话继续。
一句话里有多件独立事项，就分别派发；每件有一个不超过 12 个字的中文短标题和一句话目标。
补充：只有当新消息明确指向某个运行中任务（回复了该任务的消息，或明确说「那个任务」且只有一个候选）才补充到该任务；
否则作为新事项；有多个候选又无法确定时先问一句。
问候、引用、愿望、能力提问不得当作任务。
```

要求：

- 给用户看的 `title`（短标题）与给执行器的 `work_brief`（完整说明）分开，不要把后者暴露在卡片上。
- 现有意图守卫（记账、引用、能力问句等）保持不变。
- 对工作页的 CC/Codex 聊天不改变「可信人工聊天，直接发送」的语义。

### 4.8 补充去向提示与撤销（保持诚实）

- 当用户消息被判定为补充到某个任务时，在对话里给一行轻提示：「已补充到「标题」」。
- 同行给一个「改为新事项」按钮，行为必须符合输入的真实状态（沿现有 `inputs` 状态：已受理、排队、sending、delivered、unknown、revoked）：
  - 未送达（已受理／排队）：可 `revoke` 该输入，并把同一正文作为新事项提交（用新的 `request_id`）。
  - 已送达（delivered）或 unknown：**不能声称撤回**。只提供「另开新事项」，并明确提示「原任务已收到这条补充」。
- 补充输入沿用任务的持久输入队列与来源绑定，不新建旁路。

### 4.9 步骤「人话化」

- 在客户端新增一个事件到文案的映射函数（含单元测试）：
  - 搜索 → 「搜索了 N 个来源」；读取文件 → 「读取了 N 个文件」；修改文件 → 「修改了 xxx」；运行测试／命令 → 「运行了测试（通过／失败）」；等待用户 → 「等待你的回应」。
- 连续同类调用折叠为一行，**N 必须来自真实事件计数**。
- 点开可看原始工具名、参数摘要、输出摘要。
- 没有结束事件的工具调用不显示为完成。
- 无法识别的事件显示中性文案（如「执行了一项操作」），**不得编造成功或结果**。
- 若后端 `work_events` 已含可用字段则直接用；是否需要服务端补充 `label`/`summary` 字段，先在核验报告里判断，倾向先做客户端映射。

### 4.10 产物卡

- 统一展示 `artifacts` 中真实存在的内容：文件、链接、报告／总结。
- 提供「打开 / 复制 / 分享」中当前能真实实现的动作；做不到的类型只显示名称与路径，不假装能预览。
- 没有产物就不显示产物区。

### 4.11 最小「能力目录」（只读）

- 新增只读工具 `capability_search`，数据来自**现有** `CapabilityRegistry`，返回：能力名、适用场景（若已有描述）、提供者、验证状态（已发现／已加载／已验证）、最近验证时间。
- 不得在没有证据时标「已验证」；字段缺失就如实返回缺失，不编造。
- 不新增新的数据源。让 Pi 主线提示词知道可以用它来决定派给谁、任务说明里附哪个 Skill。
- 如果现有 Registry 信息过于稀薄，只交付工具与空数据时的诚实返回，并在报告中说明下一步需要用户决定的内容。

## 6. 验收场景（必须逐条跑并留证据）

1. 发「你好」「这个月餐饮花了多少」：直接回复，**没有任务卡**。
2. 发一个明确的长任务：该消息下出现一张卡；输入框立即可用；可继续发下一条消息。
3. 一句话含两件独立事项：出现两张卡，各有短标题。
4. 任务运行中发补充：出现「已补充到「…」」；未送达时「改为新事项」可用且结果正确；已送达时只给「另开新事项」并有如实提示。
5. 点任务卡进入详情；返回回到对话并定位到原消息。从今天页进入详情，返回今天。
6. 任务完成：卡折叠成一行，结果回到对话，详情里可看到产物与步骤。
7. 工作页里和 Claude/Codex 聊天：不出现在任务台账、不出现「待验收」。
8. `unknown` 任务：显示「需要你核实」，没有任何自动重放。
9. 断网／重开 App：状态不说谎，不重复提交，outbox 与回执正常。
