## 0. 背景与核心判断

Com! 当前已经具备：

- 原生 Pi RPC 子进程（`pi_rpc.py`）、Codex app-server、Claude Agent SDK；
- 持久 outbox、稳定 `request_id`、来源绑定、`CapabilityRegistry`（`capabilities.py`、`capabilities.sqlite`）；
- `goals.py`（目标、事件、plan node、`depends_on`），**但目标定时调度当前关闭**；
- 独立的 Judge、完整权限执行器。

所以 Com! **不需要换底座**，也不需要把 App 改接到别的项目。开源项目的价值只在于：**借它们已经验证过的设计，补 Com! 缺的几块**，主要是：主动性（心跳）、一键卡片、记忆分层、技能晋升流程、秘密管理，以及对照官方协议审计现有 Pi 接入。

## 1. 硬性约束

### 1.1 继承任务 A 第 3 节的全部约束（逐条有效）

尤其是：保持 `request_id`、outbox、来源绑定、「未知不自动重放」；不重新加入只读门槛；不新增与 task 重复的「真源」；不清空数据库；测试不写生产账本；不 push。

### 1.2 供应链与执行安全（本任务新增，违反即失败）

1. **所有第三方仓库只克隆到临时目录**（如 `/tmp/com-research/`），不得放进 Com! 仓库、不得放进 `~/AI_Work_System`。
2. 安装依赖一律 `npm install --ignore-scripts` / `npm ci --ignore-scripts`；**不运行**第三方仓库的 `postinstall`、安装脚本、Telegram/Discord 机器人或任何网络服务。官方 Pi 自己也是这样做的。
3. **不使用真实的 Bot Token、API Key、Com 配对密钥**去跑任何第三方代码；需要运行就用无令牌的 CLI 模式并断开网络，或完全只读源码。
4. **不在生产 Pi 上安装任何第三方 Pi 包**（`pi install ...`），也不修改生产 Pi 的 `settings` 去加载外部扩展。需要试用的，在隔离目录、独立 `PI_*` 配置下做，并在报告中说明。
5. **复制代码前先查 `LICENSE` 文件**，逐文件记录来源、许可证、是否复制。默认策略是**按设计重新实现，不整段拷贝**；若确需拷贝，保留版权与许可声明，并在 `docs/THIRD_PARTY_NOTICES.md` 登记。
6. 不得因为某个项目「很火」而引入其整套运行时；Com! 的 task 层、outbox、能力目录是已验证资产，**不被替换**。
7. 自动化「自我进化」类能力（自动改写技能、自动晋升）**默认不启用**，见 B5。

## 4. 阶段 B2：心跳式主动性（先影子模式，再受限启用）

借鉴 `pibot` 的心跳设计，但按 Com! 的约束落地。**目前目标定时调度关闭，这个状态在本阶段结束前不得改成「默认开启」。**

设计要求：

1. **临时廉价模型会话**：每个 tick 用一次性会话，不触碰主会话缓存与上下文；输入是紧凑摘要：当前运行任务、待我决定事项、近期事件、用户可编辑的 `HEARTBEAT.md` 清单（路径放在 AI System 下由用户可编辑的位置，先在报告里确认路径，不要擅自创建到别处）。
2. **输出受限**：每个 tick 只允许一次结构化决定：`nothing` / `note`（写入事件日志，不通知）/ `speak`（给用户一条短提示）/ `escalate`（提议一个任务，**以 proposal 形式出现，由用户批准**，不得直接启动执行）。
3. **影子模式（默认）**：tick 只记录「它本会怎么决定」到事件日志，**不发送任何通知、不创建任何 task／proposal**。提供一个只读诊断入口（设置里的诊断页即可），能看到最近 N 次 tick 的输入摘要、决定与理由。
4. **预算与护栏**：每日最大 tick 数、单次 token 上限、静默时段、全局暂停开关（设置里一个开关）、有运行中任务数超限时不 tick、去重（同一原因短时间内不重复触发）。
5. **受限启用（影子模式验证后，且需要用户在设置里手动打开）**：`speak` 只进入今天页的「仅供知情」分区，**不触发系统推送**；`escalate` 只生成待我决定的 proposal。
6. 每一次触发都必须记录**触发原因**，用户在详情里能看到「它为什么现在做这件事」。
7. 不使用 push 通知作为任务事实的来源；通知只负责提醒，事实以后端记录为准。

测试：tick 决策解析、预算与静默时段、影子模式不产生副作用、暂停开关、去重、护栏失败时静默降级。

## 5. 阶段 B3：提醒卡的一键动作

借鉴 `pibot` 的「创建后立刻出卡片，带 ✅ / +10 分钟 / +1 小时 / 取消」。

- 只作用于 Com! **已有**的提醒扩展与日历能力，不新增提醒数据库。
- 在对话流（作为一种内联卡）与今天页提供：确认、推迟 10 分钟、推迟 1 小时、取消。动作必须落到真实提醒记录并回读确认；失败如实显示，不假装成功。
- 「承诺追踪（promise）」**只出设计，不实现**：当前没有独立个人 todo 实体，这是产品决策。在报告里给出 2 个方案（复用 goals / 单独轻量实体）及各自对 task 台账「真源」约束的影响，等待用户拍板。

## 6. 阶段 B4：记忆分层——只做审计与设计，不改注入逻辑

借鉴 `pi-chat` 的「账号级＋频道级」两层记忆。Com! 的记忆在用户的 AI System 目录里，由多个 Agent 共同写入，**直接改注入逻辑风险高**，所以本阶段只交付文档：

1. 审计：Pi 主线当前从哪些文件读取哪些记忆、注入时机、大小、是否有来源与更新时间。
2. 设计：建议的四层——用户长期偏好 / 项目知识 / 当前任务上下文 / 程序事实（数据库，由程序更新，模型不得改写）；每条长期记忆应带来源、更新时间、所属项目、是用户明确说明还是系统推断、是否已撤销。
3. 列出迁移成本与回滚方案。
4. 产出 `docs/COM_MEMORY_LAYERING_PROPOSAL.md`，由用户决定是否实施。

## 7. 阶段 B5：技能晋升流程——只做设计，并说明它不是安全边界

借鉴 `pibot` 的「提议 → 护栏 → 暂存 → 评测 → 晋升」。

- 设计一个暂存区（例如 AI System 下的 `Skills/drafts/`）与晋升流程：护栏（结构合法、体积上限、补丁可应用）、至少一次真实低风险样例评测、**晋升必须由用户在 App 里点确认**、晋升时留 Git 提交。
- 明确写清：Com! 的 Agent 拥有完整权限，**暂存区是约定与评审流程，不是访问控制**；它的作用是让改动可审查、可回退。
- 默认**不启用**自动晋升。设计文档给出一个只读的「技能草稿待审」入口位置建议（今天页知情分区）。
- 产出 `docs/COM_SKILL_PROMOTION_PROPOSAL.md`。

## 8. 阶段 B6：秘密管理——只做设计

借鉴 `pi-chat` 的运行时秘密交换（Agent 看不到真实密钥，由用户授权后加密传递，执行边界注入）。
