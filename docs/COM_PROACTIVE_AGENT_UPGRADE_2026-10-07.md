# Com! Personal Agent 主动性升级方案

> 2026-10-07 · 产品与实施方案。现场核对对象：当前 iOS 源码、Mac mini 生产排期与事件记录。下文明确区分已实现与拟实施；示例日程、金额和目标均为交互示意，不是你的真实记录。本文不代表已部署整套升级。

## 实施后的范围

本轮按用户后续修正落地：记账作为今天页的大模块；双机项目看板放在工作页，行动建议联动到今天。已交付、真实测试及未完成边界见 [实施报告](COM_PERSONAL_AGENT_DELIVERY_2026-10-07.md)。以下保留完整升级愿景，不将所有规划项标为已实现。

## 1. 产品要替你承担什么

**Com 应该持续记挂你在意的事：提前发现问题，整理好信息，准备下一步，按合适的时机找你，并跟进到结果。**

核心指标不是每天说了多少话，而是每周帮你少漏了什么、推进了什么、少花了多少精力。

建议建立四个明确承诺：

1. **每天替你看一遍。** 固定时间整理安排、待决事项和目标，给当天最值得做的一步。
2. **重要变化主动说。** 截止、冲突、结果、阻塞发生实质变化时才来找你；相同事情不反复刷屏。
3. **能准备的先准备。** 提醒会议前先整理材料；提醒续费前先查已有账单；催交付前先列缺项。
4. **你说完之后有人跟。** “帮我盯着”形成持久事项；答应的事能继续推进，失败会说明，完成有证据。

它的工作方式：**观察 → 关联事项与目标 → 判断是否值得行动 → 准备或执行 → 适时联系你 → 跟进结果。**

## 2. 现状核验：缺口在哪里

| 能力 | 2026-10-07 现场事实 | 下一步增量 |
|---|---|---|
| 主聊天与后台执行 | 已有持久消息、任务、回执与真实 Hermes 运行；此前一次开发直接占用主聊天约 27 分钟 | 耗时任务持续转后台；短消息不排在长开发之后；用户能看到谁在负责与当前阻塞 |
| 固定主动消息 | mini 已配置 09:00 晨报、21:00 复盘，未暂停；两次试发事件完成，主聊天有收据 | 固定日报产品化：App 内可配置、可追溯、跨来源摘要、来源过期降级、错过时合并补报 |
| 个人观察 | 已启用非影子模式；当前 `heartbeat.digest()` 主要读取任务、建议和近期观察 | 增加日历、账务、事项、目标和来源健康，形成跨领域判断；不是只盯开发任务 |
| 长期目标 | 已有 goals/events 与目标建议接口；生产 goals 表为 0，目标调度未开启 | 目标建档、每周推进、停滞识别、证据更新、暂停与恢复；不能靠打开空调度器解决 |
| 数据整合 | 已有 personal_hub 的事项、反馈、来源及关联基础；iOS 今天页仍偏数据分区展示 | 从“日历一栏、账本一栏”升级为“同一件事的一张卡”，跨源关联须保留证据 |
| 手机提醒 | 本轮已安装含后台刷新通知的 iOS 构建；通知授权与真实后台到达未验收，尚无 APNs 远程推送 | 生产主动性需要 APNs + 持久通知队列；生成、推送受理、用户打开分别记录 |
| 回复风格 | 简短、自然、结果优先的共享规则已写入源码；尚未完成重载和真实模型验收 | 普通回复默认 1–3 句、约 100 字内；复杂内容分层展开，保留关键事实 |
| 光效语音 | 保留现有自定义声量光效和转写动效；常用控制扩展编译通过，装机缺新增签名配置 | 依最新选择保留自定义面板；控制入口仍会切到 Com，不声称跨 App 悬浮 |

早期 Hermes cron 的晨报只输出到本地日志，未投递主聊天；本轮已打通主聊天收据。**定时生成、手机提醒、持续推进目标是三个独立交付，不能把其中一个当成全部完成。**

## 3. 一天的使用方式

### 固定节奏

以下是建议的默认值，晨报和晚报时间沿用现有排期。新增周报、中午检查等是规划，未启用。

| 时间 / 触发 | Agent 做什么 | 你看到什么 |
|---|---|---|
| 08:45 起准备，09:00 晨报 | 读取已连接数据、核对新鲜度、找冲突、挑当天重点 | 一句结论 + 最多 3 项 + 一个最值得点的行动按钮 |
| 中午内部检查 | 看上午的计划是否变了、是否出现新阻塞 | 默认不通知；确实影响下午安排才发一条 |
| 事件变化时 | 截止临近、会议变更、工作完成、执行失败等 | 一条有原因、有下一步的消息；细节折叠 |
| 21:00 晚间复盘 | 核实今天的推进，整理未结事项，准备明天第一步 | 做成了什么、留给明天什么；没有变化也可只有一句 |
| 周日 20:30 周复盘 | 对照目标与证据，检查投入、阻塞和下周容量 | 最多 3 个本周结论、下周最多 3 个重点；替代当天晚报，避免叠加 |

周末、出差和休假使用不同节奏，但只依据明确日历或你的确认切换；不能把打开 App 晚推断成睡懒觉。时区明确显示，初始使用 Asia/Shanghai。

**晨报示例（虚构）：**

> 今天先把评审稿定下来，下午两点要用。我把缺的两页和上次意见放在一起了。另有一笔订阅明天续费，晚上再决定也来得及。
>
> `[看准备材料]` `[留 30 分钟处理]`

点开后才展示真实来源、材料清单、日程范围与同步时间。只有材料已经产生且能打开，才允许说“放在一起了”。

## 4. 六个功能模块

### A. 今日主张：告诉你今天怎么过

今天页不再只是列数据。首屏回答三个问题：**今天最重要什么、现在可以做什么、什么需要我决定。**

- 顶部压缩成日期、小头像与状态入口，取消大面积问候和重复说明。
- 第一张卡只给一个主张：结论、为什么现在、下一步；正文约 40–100 字。
- 最多 3 条待你决定，其余进入“全部”。每项一个主操作，另一个稍后或忽略。
- “我在替你推进”显示真正运行中的事项、成果与阻塞；不用循环动画伪造工作。
- 真实安排、近期目标随后；账本、健康、原始日历作为详情，不占首屏。
- 数据缺失时显示“日历昨天后未同步，无法判断今天全部空闲”，不能用空列表给确定建议。

### B. 事项中心：同一件事只维护一个状态

一件事可能同时出现在聊天、邮件、日历和任务里。它应该合成一个可追踪的“事项”，而不是四条互不认识的通知。

每个事项保存：标题、涉及来源、事实与推断、负责人、截止时间、当前阻塞、下一步、相关目标、下次检查时间和完成凭据。

例：某次拍摄的日程 + 对方确认邮件 + 材料清单 + 后期任务，组成同一事项。来源冲突要显式保留；没有关联证据不自动合并。

在主聊天、今天页、推送中展示同一事项的不同视图；只有一份状态。已处理、延期、停止关注在各端立即一致，旧通知不能重新把事情变成待办。

### C. 目标伙伴：持续推进，不只提醒截止

目标与任务分开：目标是想实现的结果，任务是下一步，习惯是可选的重复行动。

一个有效目标至少有：想要的结果、完成证据、当前起点、下一步。截止日、每周可投入时间、禁区按需补充；用户没给的数值不虚构。

建议首轮只选 1–3 个真实目标，避免把每次愿望自动变成长期义务。Agent 可以发现候选目标、给一句理由；未经你采纳的候选不进入执行和提醒计划。

- 每个目标固定每周复看；截止或阻塞变化时提前检查。
- 每次只给可完成的下一步，估算时间明确为估算。
- 卡住时区分：没时间、条件不足、路径无效、目标不再重要。不要只重复“加油”。
- 连续未推进时先缩小下一步或建议暂停，不无限加提醒。
- 自动完成仅依据真实成果、相关业务状态或你的确认；不能凭聊天次数生成百分比。
- 已授权范围内可主动查资料、整理材料和执行；承诺、发送、共享或不可逆动作遵守已有明确授权。

**目标建议示例（虚构）：**

> 这周可用时间不多。先把下一期的提纲定下来，比同时推进三个选题更实际。我能先整理你已收藏的相关材料。
>
> `[准备材料]` `[换个重点]` `[本周暂停]`

### D. 行动包：来找你时，已经准备了一步

这是最能让它区别于聊天 App 的增量。

| 场景 | 普通提醒 | Com 应交付的准备 |
|---|---|---|
| 会议或拍摄前 | “快到时间了” | 议题、上次结论、待确认问题、相关材料入口；交通信息必须有来源才给 |
| 项目截止前 | “还没完成” | 差哪几项、阻塞在哪里、已生成的草稿、最小可交付范围 |
| 订阅到期 | “明天扣费” | 核验过的金额和日期、已有历史账单、管理入口；没有使用数据不猜“你不常用” |
| 工作结果完成 | “任务完成” | 能打开的成果、已验证内容、仍需你实际检查的一步 |
| 空档出现 | “你有空了” | 基于完整已同步日历和待办，建议一个匹配空档的短任务；不把未记录时间当承诺空闲 |
| 收藏堆积 | “你收藏了很多” | 关联当前目标的少量资料摘要和可用输出；无目标关联则留在资料库 |

### E. 关注与发现：补上你没有想到的东西

不做泛资讯瀑布流。只有能说明“为什么与你有关”的内容才进入发现。

第一批候选能力：

1. **承诺漏项**：你说过“下周把这个发过去”，到期前能找回对象和草稿；对象不明就询问，不能擅自发送。
2. **计划容量冲突**：本周目标工作量明显超过已有可用时间，建议减少重点；用区间而非虚假的精确工时。
3. **决策反复拖延**：同一选择多次延后，整理选项和代价，询问是否取消或换方向。
4. **等待他人的事项**：到约定节点提醒你；未授权不替你催第三方。
5. **与目标有关的新变化**：已订阅主题、选定信息源里的更新，附日期、来源和具体影响；无新增就不发。
6. **个性化机会**：收藏、日历和项目之间存在明确联系时，建议可复用材料或合并安排。标作建议，不当作既定计划。
7. **资料失联**：某来源长时间没更新，合并提示一次修复入口，避免每天假装掌握最新情况。

发现类每周默认最多一组精选，先服务当前目标；不是为了表现“聪明”制造新目标。

### F. 反馈与学习：越来越会拿捏分寸

每张主动卡提供少量动作：`现在处理 / 晚点 / 已完成 / 不相关`；更多菜单才放“别再提醒这件事”“少发这类内容”。

- “晚点”改变这件事的检查时间，不自动推断你讨厌整个类别。
- “不相关”记录理由和来源，降低相似候选优先级；忽略不等于拒绝。
- “这个已经做完”马上停止重复提醒，并更新相关视图。
- 每周复盘可轻问一次“这些提醒有用吗”，不在每条后强求评分。
- 明确表达的稳定偏好才进入可查看、可纠正的长期记忆；模型推断留在临时观察层。

## 5. 主动性策略：多准备，适时说，持续跟

### 什么时候发

优先使用确定规则判断硬截止与状态变化，再让模型负责关联、摘要和建议。候选需要回答：与你什么目标有关、信息新不新、现在说有没有价值、能做什么、最近是否已经说过。

| 类型 | 默认去向 | 节奏 |
|---|---|---|
| 已确认的重要截止、真实冲突、需要你才能继续的阻塞 | 主聊天 + 系统通知 | 在有足够处理时间的节点提醒；同事项合并 |
| 一般建议、可选机会 | 今天页 | 汇总进下一次晨报或复盘，不单独打断 |
| 你交办的工作完成或失败 | 原任务 + 主聊天；通知按偏好 | 同次执行只通知一次；失败说明下一步 |
| 无变化、重复内容、低置信推断 | 内部记录或不记录 | 不通知 |

初始建议：每日 2 次固定摘要，额外非紧急主动通知最多 2 次；23:00–08:00 安静。你明确设置的临时提醒按其单独约定，不被一般摘要吞掉。达到上限的候选进摘要，不消失。当前 heartbeat 的每日 24 次是观察预算，不应被误当成 24 条通知额度。

“更主动”主要提升观察覆盖、准备成果和持续跟进；设置里提供“安静 / 适中 / 积极”，各档明确显示消息频率及可执行范围，不能暗中扩大授权。

### 什么时候自己做

- **直接准备**：读取已授权来源、去重、查资料、整理清单、生成草稿、比较方案；留下可打开的成果。
- **按既有授权执行**：在明确交办或长期范围内执行低风险、可回退的任务，回读并给结果；不重复询问已批准的事。
- **需要决定时再找你**：方向有歧义、缺必要信息，或涉及尚未授权的发送、付款、共享、不可逆更改；先准备好具体方案再问一句。

同一目标的授权、预算、范围和停止状态持久保存。任务停了、目标暂停了，后台观察不能把它重新启动。

## 6. 页面与交互规划

保留底部五入口与现有视觉语言，不加侧边栏，不为了新功能再加一级入口。

| 入口 | 升级后的职责 |
|---|---|
| 今天 | 个人行动首页：今日主张、待你决定、我在推进、真实安排、目标下一步 |
| 聊天 | 一条连续对话：你发起的事、Agent 的主动消息、简短结果；任何卡片都能在这里继续讨论 |
| 任务 | 以“目标 / 执行中 / 定时”分段，区分个人目标与技术工作，不把 cron 当个人待办 |
| 记忆 | 可核对的事实、偏好、长期关注；有来源、可修改或忘记；沿用大脑图标 |
| 工作 | 复杂成果、开发 Agent 会话、文件与验收；主聊天不展示整段执行日志 |

推荐普通冷启动进入“今天”；短时间切回保留原位置；通知直达对应事项；语音入口直接打开光效面板。它是建议的新默认行为，实施时做可恢复偏好，不强制打断正在写的对话。

一张行动卡的层级：**结论 → 一句原因 → 一个主按钮 → 折叠的来源与细节**。详情页一次只展开相关块，避免“点进去全糊成一片”。

动效服务状态：声量驱动语音光晕、发送后卡片自然归位、完成时短暂反馈。首页不持续闪动催用户，不用动效掩盖加载或连接失败。尊重减少动态效果设置。

## 7. 数据与送达：产品成立的底座

### 数据接入按价值排优先级

第一批：所选日历、真实任务与目标、账本、用户主动保存的材料。第二批：授权邮箱、提醒事项、健康摘要。第三批：选定资讯源、位置等情境能力。

每个来源记录权限、覆盖范围、最后成功同步、最近错误和是否过期。连接列表至少区分：未连接、正常、暂时失败、权限过期、无可用数据；“无数据”不能显示成“没睡觉”或“没安排”。已连接可断开，失败可重试，需要授权时给准确入口。

手机健康和日历数据在各自授权范围内使用；本机可见不代表已允许同步 mini。跨源综合只能用已连接且已授权给该用途的数据。iOS 不以读取其他 App 的全部通知或屏幕作为产品前提。

### 把晨报送到手机

mini 按时间生成并先落库，再将消息 ID 放入持久通知队列。iOS 接 APNs，点通知打开同一条消息；前台通过 SSE 同步。Android 使用平台允许的可靠通知通道，共用业务消息 ID，避免两端重复提醒。

后台刷新只能补漏，不能充当准点推送：Apple 明确由系统选择后台启动时间。[Apple 后台策略](https://developer.apple.com/documentation/BackgroundTasks/choosing-background-strategies-for-your-app)。远程通知由服务端发给 APNs，再由系统处理到设备。[Apple User Notifications](https://developer.apple.com/Documentation/usernotifications/)

通知受权限、系统专注模式、网络等影响，不承诺任何条件下准点到达。监测分别记录：计划时间、开始生成、生成完成、主聊天落库、APNs 受理、用户打开；APNs 受理不能标成“你已收到”。

服务停机后恢复：固定摘要只补当前仍有价值的最新一份，并标“补报”；历史普通建议不集中弹出。来源断开时生成有范围说明的降级摘要；模型不可用时只发确定性的已确认安排或简短失败状态，不编造分析。

## 8. 实施设计：复用现有系统，补齐闭环

| 层 | 复用 | 拟新增 / 调整 |
|---|---|---|
| 资料 | `personal_hub.py`、已有日历/账务/设备接口 | 来源健康、范围、新鲜度；增量快照 |
| 事项 | 现有 matters、关联、反馈 | 统一下一步、下次检查、目标关联和完成证据 |
| 候选 | `heartbeat.py` | 从仅任务摘要扩为多源摘要；候选先入队，理由与来源可追溯 |
| 排期 | `proactive.py`、`goals.py` | App 内策略配置、晨报预生成、周复盘、目标检查、错过排期处理 |
| 生成 | `background_events.py`、Hermes | 后台整理使用独立受限生成会话，耗时执行交给已有任务层；主聊天保持可响应 |
| 消息 | `conversation.task_receipt`、现有稳定请求 ID | 通用主动消息关联事项/目标/来源、投递状态与语义去重 |
| 通知 | 现有 iOS 后台刷新 | APNs token 注册、服务端 outbox、失败重试和撤销失效通知 |
| 前端 | `TodayView`、`TasksView`、主聊天 | 今日主张卡、事项详情、目标分段、主动性设置和反馈 |

新增数据契约至少包括：`source_id / source_version / observed_at / matter_id / goal_id / next_check_at / action / evidence / dedup_key / notification_state`。同一事项的重要更新生成新版本，不因措辞不同重复通知。

执行与发消息分离：生成成功但通知失败，只重试通知；业务执行结果不确定，先查原回执，不能重跑付款、记账或发送。日志不要存凭据或把敏感正文写进锁屏通知。

性能和成本：增量变化先过规则，无变化不重复调用大模型；按类型设置生成时限、并发和每日预算，超额延到摘要；不靠全天扫描所有资料表现主动。固定晨报优先于低价值机会发现，用户新消息优先于可延后的后台整理。

## 9. 落地顺序与验收

周期是开发量估算，不是已承诺的上线日期；签名/推送账号、数据授权和实体测试可能形成外部等待。

| 阶段 | 范围与产物 | 验收门槛 | 估算 |
|---|---|---|---|
| P0：真的会来找你 | 晨晚报可配置；生成/落库/推送可观测；APNs；来源状态；简短回复规则真实验收 | 连续 7 天可追溯日报；锁屏、后台、断网恢复实测；无重复消息；失败可解释 | 3–5 个开发日 + 7 天观察，可重叠 |
| P1：告诉你下一步 | 今天页、跨源事项、行动卡和反馈；先打通会议准备、项目交付、订阅到期三场景 | 每条建议有来源/理由/下一步；点击能完成或产生真实结果；处理后不再提醒 | 5–7 个开发日 |
| P2：替你跟目标 | 1–3 个真实目标、周计划、停滞识别、准备成果、暂停与恢复 | 一个真实目标连续跟进两周；进展有证据；中途改目标不沿旧计划执行 | 5–7 个开发日 + 两周使用观察 |
| P3：更懂你 | 反馈调节、容量冲突、收藏关联、选定信息源发现、场景化节奏 | 建议相关性提升且额外打断不增加；能解释和撤销学习结果 | 依前两阶段真实反馈迭代 |

**第一条完整验收链：** 明确一个真实事项 → 获得已授权来源 → 09:00 生成简短晨报 → 手机出现真实通知 → 点开行动卡 → 执行/延期 → 回读状态 → 下一次检查不再重复旧建议。

必测失败情形：来源过期、两源冲突、模型超时、没有权限、没有健康数据、服务重启、重复事件、用户暂停、手机离线、多端同时操作、长任务运行中收到新聊天、通知被系统延迟。结果分别落到可理解的状态，不能都写“连接异常”。

## 10. 怎么判断这次升级有用

首轮用一周个人使用记录建立基线，再定改善目标，不编造提升比例。

- **真实推进**：每周由 Agent 主动准备或执行、且有成果的事项数。
- **避免遗漏**：经你确认有帮助的截止、冲突、等待提醒。
- **打断成本**：你标“不相关/太频繁”的次数、重复提醒次数；不能单用通知点击率优化。
- **目标连续性**：真实目标每周是否有可验证的下一步，卡住原因是否被处理。
- **服务可靠性**：按计划生成率、落库与推送受理延迟、打开后能否定位正确事项、失败恢复。
- **信任**：无来源的事实为零；未经授权的业务写入为零；不能凭模型宣称通过。

首版成功的感受应该是：**“我不打开它，它也在替我记挂事情；它来找我时，总带着一点已经准备好的东西。”**
