# Com! 信息架构与「今天 / 任务」改版方案

> 2026-10-03 · 用户已确认连同页面改版一起整合，现已落入 1.7.0 工作区。实现契约见 [任务层契约](TASK_LAYER_CONTRACT.md)，能力现状见 [1.7.0 升级说明](COM_1.7_UPGRADE.md)。

## 本轮实际整合

- 保留底部「对话 / 今天 / 任务 / 工作 / 更多」五个入口及白灰视觉。
- 今天页先显示待处理摘要，再显示手机日历的今日时间轴、在途工作和账本摘要。全天日程折叠；完整日历仍可进入。
- 待处理任务按真实 id 去重，点击进入对应任务详情；没有任务的主对话异常记录定位原消息。通知分析仅供查看，不计入待你决定数量。
- 任务页使用同一台账，筛选为全部、待你决定、执行中、待验收、已完成、已结束。执行结束和验收通过分别归类；停止、拒绝、过期归已结束，不冒充完成。
- 任务列表只放名称、状态、必要阻塞原因及详情入口；批准、补充、停止、结果、原文、时间线在对应详情中。授权建议使用原 proposal id，与同 id 任务合并；已派发但实际状态未同步时保留待核实。
- 从今天进入详情可返回今天；从任务列表进入可返回同一筛选列表。「回到交办消息」使用确认过的来源身份：工作页原消息回到真实工作会话，主对话原消息回到相应锚点。缺少原生来源确认时只提供实际执行会话入口，不伪造消息定位。
- 对话页的活动入口统一进入任务页，移除重复任务抽屉。通知巡检成为「更多」里的独立页。
- 工作会话统一完整操作权限；历史交办原文不改写。头像空闲时不显示状态框，忙时只显示图标与状态，卡片紧邻角色下方且不遮挡角色。

验收证据保存在 `verification/com-1.7.0/`：`layout-integration-*` 为本轮构建及真实页面测试日志，`com-today-*`、`com-tasks-active-*`、`com-avatar-header-*` 为模拟器页面截图。个人 todo 新实体仍未实现；本轮不将工作任务伪装成个人待办。

下文保留改版前的评审底稿与原方案，行号和工期属于当时快照。按钮示意中未落地的直接批准、自动重试、人工验收等操作，以本节实际行为为准；未知执行不会由页面改版自动重放。

## 一、结论

页面乱不是排布问题，是三个结构问题：

1. **同一件事有三份实现、三个入口**——任务台账在「对话 → Pi 活动」抽屉、「任务」tab、以及「今天 → 在途工作」里各渲染一次，三份逻辑还不一样。
2. **「今天」是按实现顺序堆卡片，不是按决策优先级排序**——四个元素同权重，最该看的「待我处理」排在第三屏。
3. **详情不分层**——卡片里直接铺后端字段（交办原文、事件时间线、执行详情），列表失去可扫性。

改法：**一页回答一个问题、一物一处、列表只放"状态 + 一个动作"**。

## 二、诊断（证据）

### 2.1 同一内容三处渲染

| 位置 | 代码 | 渲染内容 |
| --- | --- | --- |
| 对话页「Pi 活动」底部抽屉 | `HermesChat.kt:279-289` | TaskLedgerSection + WorkProposalSection + SignalActivitySection |
| 「任务」tab | `TaskLedger.kt:218-233` | WorkProposalSection(pending) + TaskLedgerSection + WorkProposalSection(history) + SignalActivitySection |
| 「今天」页「在途工作」 | `TodaySections.kt:64-74` | `buildLedgerTasks(...).filter{status=="active"}.take(3)`，标题走 `todayRunTitle()` |

后果：同一个后台任务在三个地方名字可能不一样（`todayRunTitle` 取 `run.title → summary → 原消息前 100 字`，任务页取 `task.title`）；「Pi 活动」抽屉与「任务」tab 完全重复，底部导航已经有一个「任务」，抽屉是多余的第二个入口。

### 2.2 任务与授权建议是两套数据源，靠 id 碰运气

`TaskLedger.kt:163`：

```kotlin
val proposal = vm.workProposals.array("items").firstOrNull{ it.optString("id")==task.id }
if (proposal != null) { WorkProposalActions(vm, proposal) }
else { Text("授权建议正在同步；允许与拒绝仅针对这项任务。"); TextButton(...){Text("刷新授权建议")} }
```

`/personal/tasks` 与 `/personal/work/proposals` 是两条独立拉取链路（`ChatUI.kt:96-105` 轮询周期还不一样：任务页 3s、其他页 10s）。id 匹配不上时，用户看到的是"正在同步 + 刷新"——**这就是"联动性差"的技术根因**，不是视觉问题。

### 2.3 「今天」页：四张同权重卡片

`PersonalOverview.kt:123-142` 的渲染顺序是 `PhoneCalendarCard()` → `FinanceOverviewCard()` → `TodaySections()`，全部是 `Surface + RoundedCornerShape(Radii.L) + Card 色 + 1dp Line`，视觉权重完全相同，排序按代码顺序而非用户优先级。

- 日历卡带 7 日条 + 事件列表，10-02 那种 4 条全天事件（休假 / 国庆节 / 黄金周 ×2）直接把首屏占满（见 `verification/com-1.5.0/phone-today.png`），「待我处理」要滚动才可见。
- 「待我处理」内部又是 5 类不同性质的东西共用一个 `TodayLine` 平铺（`TodaySections.kt:46-56`）：`needsApproval`（要批准）、`needsReview`（要回应）、`failedMessages`（要重试）、`reviewTasks`（要验收）、`important signals`（只需知情）。**需要动作的和只需知情的混在一起，且全部不可操作——只能跳页。**
- 页头有返回箭头（`PersonalOverview.kt:127`，返回 Pi）+ 副标题"手机日历直接读取 · 账本与任务由 Mac mini 同步"——tab 长得像二级页，副标题是技术实现说明。

### 2.4 任务卡：详情不分层

`TaskLedger.kt:152-215` 展开区一次性铺出：scope/directory → goal → 完成条件 → 当前阶段 → 最近一步 → 交办原文 → 约束 → 授权动作 → 审批 → 补充约束输入框 → 进入执行会话 → 回到交办消息 → result → inputs → events → 执行详情。**16 项、同一字号（Caption/BodySm）、同一颜色（Muted/Ink）**，没有"现在到哪一步、你要做什么"的骨架。

### 2.5 死代码

`PersonalSourceCards`（`PersonalOverview.kt:86`）零引用；`CalendarOverviewCard` / `FinanceOverviewCard` 的 `compact` 分支只被它调用。按 r04 只提示，本轮不动。

## 三、目标信息架构

| 页面 | 唯一要回答的问题 | 只放什么 |
| --- | --- | --- |
| 对话 | 我要交办什么、它刚才说了什么 | 消息流 + 交办入口 + 该消息绑定的状态卡 |
| 今天 | 我现在要做什么决定 | **需要动作的条目（可操作）** + 今天的时间骨架 + 一行摘要 |
| 任务 | 我交办的事现在到哪了 | 全部任务的唯一台账（含已完成、含授权） |
| 工作 | 我要自己跑一个 Claude / Codex | 手动会话 |
| 更多 | 配置与历史数据 | 日历 / 账本 / 权限 / 设置 |

三条原则：

1. **一物一处**：一个后台任务只在任务页有完整身份；今天页只放它的待办摘要；对话页只放绑定该条消息的卡。
2. **今天页只收"需要动作的"**：批准 / 补充 / 重试 / 验收，每条自带动作按钮，不是只跳转。
3. **列表只放状态 + 一个动作**，长文（交办原文、事件时间线、执行详情）进详情区。

## 四、「今天」页改版

保留你点名的四个元素，改的是**权重和形态**。

```text
┌ 今天 · 10月3日 周五                        [刷新]
│ 2 件待你决定 · 3 件在执行 · 今日支出 ¥329.90        ← 状态条（替代技术副标题，可点）
├──────────────────────────────────────────────
│ 待我处理  ②                                       ← 主卡：最大字号、默认展开
│   ⚠  批准「拉取代码」              [批准] [拒绝]
│   ⏳  补充约束 · 排查下载问题        [补充]
│   ✕  发送失败 · 查9月5日那笔        [重试]
│   查看全部 5 项 →                                  ← 带 taskDetailId 进任务页定位
├──────────────────────────────────────────────
│ 今天                                            ← 骨架，不是卡片
│   09:00 ─ 10:00   团队周会
│   14:30 ─ 15:30   岩馆拍摄
│   全天 · 休假、国庆节（折叠为一行）
├──────────────────────────────────────────────
│ 在途工作 3 · Pi 查账 / Codex 读源码          →     ← 一行折叠摘要
├──────────────────────────────────────────────
│ 本月 −¥735.47 · 今日 −¥329.90                →     ← 一行数字，不做卡片
└──────────────────────────────────────────────
```

首屏只有三个层次：**待我处理（大）> 今天时间轴（中）> 摘要行（小）**。

具体改动：

| 元素 | 现在 | 改成 |
| --- | --- | --- |
| 待我处理 | 5 类混排、不可操作、`take(3)` 无提示 | 按"是否需要动作"分组排序：**需批准 > 需补充 > 失败重试 > 待验收 > 仅供知情**；每条带主操作按钮；`take(3)` 后显示"N 项未显示" |
| 日历 | 7 日条 + 事件列表整卡，可撑满一屏 | 今天的**时间轴骨架**：全天事项折叠一行，只显示今天，未来日程进日历详情页 |
| 在途工作 | 卡片 + 3 条明细 | 一行"N 件 · 标题关键词"，点击进任务页（可带筛选） |
| 账本 | 卡片 + 币种 + 收支三行 | 一行数字（本月 + 今日），点击进账本页 |
| 页头 | 返回箭头 + 技术副标题 | 无返回（它是 tab）+ 一句话状态条 |

## 五、「任务」页改版

### 5.1 从三个平行列表 → 一条任务生命线

现状：`WorkProposalSection(pending)` + `TaskLedgerSection` + `WorkProposalSection(history)` + `SignalActivitySection` 四段并列，用户不知道先看哪段。

改成：

1. **顶部状态筛选 chip**：`待你决定 N | 执行中 N | 待验收 N | 已完成`——用筛选替代分段，默认停在"待你决定"。
2. **一条任务一张卡，状态驱动**（不是 raw status 驱动）：
   - 需要动作 → 卡内直接给动作按钮（批准 / 补充 / 停止 / 验收）
   - 执行中 → 一行进度：当前阶段 + 最近一步 + 相对时间；时间线在展开区
   - 已完成 → 结论 + 产物 + 验收状态
3. **授权建议并入任务卡**：同 id 的 proposal 就是这张卡的状态，不再单独一段。匹配不到时不要再显示"正在同步 + 刷新"，而是合并成一次请求（或让 `/personal/tasks` 直接返回关联的 proposal 摘要）。
4. **「通知巡检」移出任务页**：它不是任务，进"更多"或独立收件箱。
5. **「Pi 活动」抽屉删除**：与「任务」tab 重复（`HermesChat.kt:279`）。

### 5.2 联动性修复（P0，改动最小、收益最直接）

| 断点 | 现状 | 修法 |
| --- | --- | --- |
| 今天页 → 任务详情 | `ChatUI.kt:106` 的 `openActivity` **主动清空** `vm.taskDetailId=""` | 传入目标 id：`openActivity(taskId)`，落到任务页即展开该条 |
| 今天页 → 对话原文 | 无 | 条目卡补"回到交办消息"（`vm.returnToHermes(messageId)` 已存在） |
| 任务 → 执行会话 | 已有（`TaskLedger.kt:185`） | 保留，提到主操作位 |
| 任务 → 授权 | id 碰运气（2.2） | 后端 `/personal/tasks` 返回 `proposal_summary`，前端不再二次匹配 |

## 六、落地顺序

**P0（纯前端 + 一处后端字段，1-2 天）**

1. 今天页排序改为：待我处理 → 今天时间轴 → 在途工作一行 → 账本一行。
2. 今天页条目点击带 `taskDetailId`，进任务页定位并展开。
3. 任务页加状态筛选 chip；「通知巡检」移出。
4. 今天页去掉返回箭头与技术副标题，换成状态条。

**P1（组件级重写，3-5 天）**
5. 任务卡状态驱动重写：动作前置、时间线进展开区、字段分层。
6. 日历卡 → 时间轴组件（全天折叠）。
7. 在途工作 / 账本 → 摘要行组件。
8. 删除「Pi 活动」抽屉。

**P2**
9. 通知巡检独立收件箱。
10. 个人 todo（若指非 agent 的个人待办，需要新数据实体，见待决策 1）。

## 七、待决策

1. **todo 指什么？** 当前后端只有 `/personal/goals` 与 `/personal/tasks`，**没有个人 todo 实体**（`android/` 与 `backend/` 全库无 todo/待办）。如果指的是"我自己列的待办"，那是新增数据类型的架构决策，需要先定真源（Com SQLite 还是 AI_Work_System `_global/任务清单.md`）。
2. **今天页要不要保留"未来 14 天"日历？** 现在概览接口给的是未来窗口；方案里改成只显示今天。若要保留，建议折叠成"未来 3 天"一行。
3. **通知巡检放哪？** 「更多」内新页 / 独立收件箱 / 暂时保留在任务页底部。

## 八、不在本轮范围

- 任务层的授权语义、验收规则、执行器隔离（属 `TASK_LAYER_CONTRACT.md`）。
- 现有 1.7.0 未提交改动（`git status` 中 `ChatUI.kt` / `HermesChat.kt` / `TaskLedger.kt` 均有修改），本方案实施前需先确认该批改动已验收，避免与在途工作冲突。
